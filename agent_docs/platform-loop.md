# The platform loop (v3.2)

`cc-rig init` writes a project's config once. The v3.2 subcommands re-measure
and re-align that config over time without rerunning `init`. They read two
local state stores and the project's Claude Code session logs. None of them
make network calls during normal use (`refresh skills` is the exception, since
it can download skills).

## Subcommands

| Command | Reads | Writes |
|---------|-------|--------|
| `cc-rig savings` | session JSONLs, `~/.cc-rig/baseline.json` | baseline rollup |
| `cc-rig audit` | session JSONLs | `last_audit` |
| `cc-rig drift` | `.cc-rig.json`, generated files, `claude --version` | `last_drift_check` |
| `cc-rig refresh <area>` | `.cc-rig.json` | regenerated files, manifest, `last_refresh` |
| `cc-rig retro` | session JSONLs, baseline, `.cc-rig.json`, generated files | baseline rollup, `last_retro` |

- **savings**: 30-day token totals, cache read ratio, cost vs an uncached
  baseline, a per-week trend, and cross-project rank.
- **audit**: scores the last N sessions (default 10) on cache hygiene, model
  pinning, cache read ratio, and turns per session, and prints a tier-fit
  verdict. See "audit and session logs" below.
- **drift**: reports three differences from a fresh generation: generated
  files edited on disk, `.cc-rig.json` changed since init (`config_hash`
  mismatch), and the installed Claude Code version versus the version cc-rig
  is pinned to. Read-only.
- **refresh `<area>`**: re-runs one generator into a temp directory, shows a
  unified diff against the files on disk, and writes on confirm. Areas:
  `agents`, `commands`, `skills`, `rules`, `settings`, `playbook`, `all`;
  `plugins` and `hooks` are aliases of `settings`. Flags: `--yes`,
  `--dry-run`, `--json`. Overwritten files are backed up by `FileTracker`,
  the same as `cc-rig init`.
- **retro**: combines a 7-day savings report, an audit, and a drift check into
  one view, and appends the week to the baseline.

## Project state: `.claude/cc-rig-state.json`

Schema version 1. Fields:

- `created_at`, `config_hash`, `config_snapshot`
- `last_audit`, `last_drift_check`, `last_refresh`, `last_retro`

`config_hash` is `sha256` over the resolved config (`ProjectConfig.to_dict()`)
with `created_at` and `cc_rig_version` removed, so it changes only on a
meaningful config change, not on a version bump or regeneration. The file is
written at init. On regeneration `config_hash` and `config_snapshot` are
refreshed; `created_at` and the `last_*` timestamps are preserved. It is
git-friendly and contains no raw paths or user content.

## User baseline: `~/.cc-rig/baseline.json`

Schema version 1. Weekly savings rollups per project, keyed by a hash of the
project path. `savings` and `retro` append to it; `audit`, `drift`, and
`refresh` do not touch it. No raw paths or user content are written.

## Return trigger

Two mechanisms, both generated by default:

1. A single static line at the end of generated `CLAUDE.md` pointing at
   `/cc-rig retro`. It is identical on every generation, so it does not change
   the cache prefix.
2. The `session-context` SessionStart hook reads
   `.claude/cc-rig-state.json` and prints one line when `last_retro` (or
   `created_at` when there is no retro yet) is 7 or more days old. It exits
   silently when `python3` or the state file is absent.

## audit and session logs

Claude Code session JSONLs contain assistant events (model, token usage,
`tool_use` blocks) but not slash-command invocations. `audit` therefore
reports signals that are present in the logs (CLAUDE.md edits mid-session,
model switches, cache read ratio, assistant turns per session) rather than
slash-command chain compliance.
